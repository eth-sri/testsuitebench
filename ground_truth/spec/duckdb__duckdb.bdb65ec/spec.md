# DuckDB-compatible command-line database

## Spec 1: Deliverable and compatibility target

Provide exactly one runnable artifact at the workspace root named `executable`. It must be a Linux command-line program that combines an embedded analytical SQL database with the DuckDB shell interface. It is invoked directly; no server is involved.

The behavioral target is the DuckDB command-line interface and SQL engine represented by this specification. Where SQL syntax has its conventional meaning, use DuckDB semantics rather than SQLite, PostgreSQL, or another database's differing behavior. Results, types, diagnostics, persistence, catalog contents, and shell rendering are all observable.

The compatibility build deliberately identifies itself as version `v0.0.1`, even though it supports the modern DuckDB features below:

- `--version` and `-version` succeed and write exactly one stdout line, with no preceding or following metadata-only line and no stderr. That line is `v0.0.1 (Unknown Version) 780a7396`.
- SQL `version()` returns the single string `v0.0.1`.
- `.about` begins with `DuckDB v0.0.1 (Unknown Version)` and describes DuckDB as an in-process analytical, columnar/vectorized database maintained by the DuckDB Foundation under the MIT License, with the duckdb.org and GitHub URLs.
- Extension locations and download URLs use the version directory `v0.0.1` and platform directory `linux_amd64`.

The program must not crash, assert, hang, or report an internal error for valid input or ordinary invalid input. Individual invocations are expected to complete within 30 seconds, including queries over tens or hundreds of thousands of generated rows.

## Spec 2: Invocation and command processing

The general form is:

```text
executable [OPTIONS] [FILENAME] [COMMAND ...]
```

With no database filename, or with `:memory:`, use a private in-memory database. A non-option filename opens that DuckDB database, creating the file if it does not exist and its parent directory exists. Every positional argument after the database filename is a separate command and is executed in argument order. Each such command may be SQL or a standalone dot command: for example, `executable :memory: "SELECT 1" "SELECT 2"` executes both queries, while SQL that creates tables may be followed by a positional `.tables`. Paths may contain spaces and Unicode. An existing zero-byte file is not treated as a new database: opening it exits 1 with `IO Error: The file "PATH" exists, but it is not a valid DuckDB database file!`. A nonempty file with an invalid DuckDB header is likewise rejected cleanly.

Support both stdin-driven operation and these command sources:

- `-c COMMAND` and its alias `-s COMMAND` execute SQL or one standalone dot command. A command can contain multiple semicolon-delimited SQL statements. Repeated `-c`/`-s` options execute in order.
- `-f FILENAME` reads and executes a SQL script, including comments, multiline statements, transactions, dot commands, and multiple result-producing statements. Repeated `-f` options are supported.
- `-cmd COMMAND` executes before ordinary stdin. Repeated `-cmd` values retain their order.
- `-init FILENAME` loads the named initialization script before command-line commands. Without `-no-init`, the normal user initialization file is honored when present. If `-no-init`/`--no-init` occurs anywhere in the invocation, it suppresses all initialization processing, including an explicit `-init FILENAME`, regardless of the relative order of the two options.
- `-no-stdin`/`--no-stdin` prevents reading stdin after all explicit commands. `-batch`/`--batch` forces noninteractive operation.
- With no terminating command option, read all of stdin. Recognize multiline SQL, comments, quoted newlines, multiple statements, and shell dot commands. State created by earlier statements remains available to later statements in the same process.

The option parser accepts the tested double-dash spellings `--ascii`, `--box`, `--column`, `--cmd`, `--csv`, `--echo`, `--header`, `--html`, `--init`, `--json`, `--jsonlines`, `--line`, `--list`, `--markdown`, `--newline`, `--noheader`, `--nullvalue`, `--quote`, `--readonly`, `--safe`, `--separator`, and `--table` as aliases of their corresponding single-dash options. These aliases have identical argument handling, ordering, output, and exit behavior. In particular, they remain valid when combined with single-dash `-c`, `-s`, or `-f`, and when commands are supplied through stdin.

Initialization happens before `-cmd`; explicit command/file sources otherwise execute in command-line order. When initialization has not been suppressed, a successful explicit `-init FILENAME` writes an ANSI-styled notice to stderr whose visible text is `-- Loading resources from FILENAME`; it does so even with `-no-stdin`. A `-cmd` failure prevents later stdin processing. An initialization failure prints a loading/opening diagnostic containing `Encountered errors while executing init file`, prevents the main command, and exits unsuccessfully. A missing `-f` file exits 1 with an `IO Error`. A missing explicit init file does the same only when initialization is enabled; with `-no-init`, it is not opened, produces no diagnostic, and the invocation exits 0 if there is no other work or error. Inaccessible database paths fail clearly.

`-echo` echoes each command before its result. `-bail`, and `.bail on`, stop at the first SQL or script error. Without bail, stdin processing continues with later statements after a recoverable SQL error, but the eventual process status remains unsuccessful. Repeated `-c`/`-s` processing is different: if one command fails, later command-line commands are not executed. A failed one-shot `-c` exits with status 1. Successful work normally exits 0. `.exit CODE` exits with that code; `.quit` exits successfully. `-no-stdin` with no work exits successfully with no stdout.

`-h`, `-help`, and `--help` succeed and describe `FILENAME`, `[SQL]`, and all supported options. Help uses the shell's ANSI styling even when captured: bold headings, green option/command names, yellow argument syntax, and reset sequences. The options heading is the uppercase text `OPTIONS:`. The option inventory includes `-ascii`, `-bail`, `-batch`, `-box`, `-column`, `-cmd`, `-csv`, `-c`, `-echo`, `-f`, `-format`, `-format-file`, `-init`, `-header`, `-h`, `-help`, `-html`, `-interactive`, `-json`, `-jsonlines`, `-line`, `-list`, `-markdown`, `-newline`, `-no-init`, `-no-stdin`, `-noheader`, `-nullvalue`, `-quote`, `-readonly`, `-s`, `-safe`, `-separator`, `-storage-version`, `-table`, `-ui`, `-unredacted`, `-unsigned`, and `-version`. The `-?` option is not help: it exits 1 with an “Unrecognized option '-?'” diagnostic and suggestions. Unknown options likewise exit 1, name the option, offer likely choices, and direct the user to `-help`.

`-format` and `-format-file` use the separately supplied autocomplete extension, but their unavailable-extension behavior is asymmetric in this build. With no autocomplete extension, `-format "select 1"` exits 0 and writes nothing to either stream. `-format-file EXISTING_FILE` writes a `Catalog Error` to stderr explaining that `duckdb_format_sql` exists in the autocomplete extension and suggesting `INSTALL autocomplete;` and `LOAD autocomplete;`, but it too exits 0 and produces no stdout.

## Spec 3: Databases, access modes, and safety

Disk databases persist schemas, data, views, indexes, sequences, macros, and transactionally committed changes across separate invocations. Distinct files remain isolated. The implementation supports large databases, Unicode identifiers, files on read-only filesystems, clean shutdown with outstanding or rolled-back transactions, checkpoints, and concurrent read-only opens.

`-readonly` and its alias `--readonly` open the primary database read-only with identical behavior. SELECT, metadata/PRAGMA queries, persistent views, and in-memory temporary tables remain usable under either spelling. INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, and other persistent changes fail with a nonzero status and an error identifying the statement type and the read-only attached database. Failed writes do not modify either file contents or logical data.

`-safe`, its alias `--safe`, and `.safe_mode` enable the same locked-down mode while still permitting ordinary in-memory relational SQL. Safe mode blocks filesystem reads/writes, `COPY` to files, `ATTACH`, extension loading, `.cd`, `.shell`/`.system` and the `.sh` alias, `.import`, `.read`, `.output`, `.once`, `.log`, `.excel`, and equivalent indirect access. It also locks security-relevant configuration changes. Blocked dot-command diagnostics use the exact phrase `cannot be used in -safe mode`: `.sh` and `.system` report `.sh/.system cannot be used in -safe mode`, `.import` reports `.import cannot be used in -safe mode`, `.cd` reports `.cd cannot be used in -safe mode`, and `.output` or `.once` reports `.output/.once/.excel cannot be used in -safe mode`. The same dot-command diagnostics apply after safe mode is enabled with `.safe_mode`. SQL-level blocking uses configuration diagnostics instead: `COPY` to a file and `read_csv` exit 1 with `Permission Error: Cannot access file "PATH" - file system operations are disabled by configuration`; `ATTACH` uses the same text with the resolved absolute path; and `LOAD json` reports `Permission Error: Loading external extensions is disabled through configuration`. These SQL diagnostics do not contain the words `safe mode`. Safe mode works with both memory and persistent databases under either option spelling.

`-storage-version VER` (also accept `-storage_version`) controls the format of a newly created database; the advertised default is `v0.10.0`. Accept `latest`, `v0.10.0`, `v0.10.1`, `v0.10.2`, `v0.10.3`, `v1.0.0`, `v1.1.0`, `v1.1.1`, `v1.1.2`, `v1.1.3`, `v1.2.0`, `v1.2.1`, `v1.2.2`, `v1.3.0`, `v1.3.1`, `v1.3.2`, `v1.4.0`, `v1.4.1`, `v1.4.2`, `v1.4.3`, `v1.4.4`, `v1.5.0`, `v1.5.1`, `v1.5.2`, `v2.0.0`, and `latest`. An invalid value names the bad version and lists valid values in a stderr diagnostic containing the capitalized label `Error` and the category `Invalid Input Error`; for example, `invalid_ver` is described as `The version string 'invalid_ver' is not a known DuckDB version`. This invalid-argument metadata path exits with status 0 without executing the supplied SQL. Databases written using requested compatible versions can be reopened and queried.

## Spec 4: Result rendering

Every result set has DuckDB CLI formatting, including correct column names, logical type names, alignment, escaping, row boundaries, and final newline. Output flags can occur more than once; the last selected format applies to subsequent commands, so formats may be switched between commands. `-header` and `-noheader` toggle headings in modes that honor the header setting. Markdown is an exception: `-markdown -noheader` still emits both the column-heading row and the alignment row before its data. `-nullvalue TEXT`, `-separator TEXT`, and `-newline TEXT` set null, column, and row representations. Multi-character separators, tabs, empty null strings, Unicode, embedded quotes/commas/newlines, NUL bytes, long names, wide values, empty strings, high-precision numerics, dates/times, nested values, infinities, and NaNs must render correctly.

Support these modes and their dot-command equivalents:

- The default `duckbox` form is a Unicode box-drawing table that includes column-name and type rows and right-aligns numeric cells. For `SELECT 42 AS answer`, the shape is:

  ```text
  ┌────────┐
  │ answer │
  │ int32  │
  ├────────┤
  │     42 │
  └────────┘
  ```

- Explicit `box` mode also uses an aligned Unicode box-drawing grid, but is distinct from duckbox and omits duckbox's type row and adaptive presentation. `table` uses an aligned ASCII `+`, `-`, and `|` border. `column` uses padded columns and a dash underline. `markdown` uses a pipe table and type-appropriate alignment markers. `line` prints aligned `name = value` pairs, with separate blocks for rows.
- `csv` is standards-compliant comma-separated output with a header by default and proper double-quote escaping. `list` is unquoted separator-delimited text, pipe-separated by default; unless changed with `-nullvalue` or `.nullvalue`, every SQL NULL in list mode is rendered as the four characters `NULL`, not as an empty field. `tabs` uses tabs. `ascii` emits fields on separate lines without a table. `quote` uses pipe separators, single-quotes strings and headings, escapes contained text, and leaves numeric values unquoted.
- `json` emits an array of objects keyed by column name. Each object is internally compact, but a multirow result is line-broken: the first row begins immediately after `[`, subsequent rows are separated by `,\n`, and the last is followed by `]\n`. Thus two integer rows render as `[{"n":0},\n{"n":1}]\n`; a single row remains on one line, and no rows is `[]\n`. `jsonlines` emits one compact object per row and emits exactly one newline for an empty result. SQL NULL is `null`. Integers and floating-point values are number primitives, while SQL BOOLEAN values are the lowercase strings `"true"` and `"false"`, and DECIMAL values are strings that preserve precision. This renderer is JSON-like rather than valid JSON for complex values: `['x','y']` renders as `[x, y]`, `{'a': 2}` as `{'a': 2}`, and `MAP {'a': 2, 'b': 3}` as `{a=2, b=3}` inside the enclosing object. String newlines are escaped as `\n`.
- `html` emits `<tr>`, `<th>`, and `<td>` fragments with HTML escaping. `latex` uses its conventional escaped tabular representation. `tcl` double-quotes every heading and field: `.mode tcl` followed by `SELECT 1 a, 'hello' b;` emits `"a" "b"` and then `"1" "hello"`. `insert` emits SQL INSERT statements and accepts an optional target table name. For `.mode insert mytable` followed by `SELECT 1 a, 'hello' b;`, the exact row is `INSERT INTO mytable(a,b) VALUES(1,'hello');`: a simple target is not double-quoted, and the column list is emitted. `trash` discards result data. Supplying a table argument to another mode fails with status 1 and the diagnostic `TABLE argument can only be used with .mode insert`.

For orientation, representative single-row renderings are `id|name|value` then `1|Alice|42` in list mode, `'id'|'name'|'value'` then `1|'Alice'|42` in quote mode, and `[{"id":1,"name":"Alice"}]` in JSON mode. Output modes must follow DuckDB quoting rules rather than merely containing these values.

Duckbox controls include `.maxrows`, `.maxwidth`, `.columns`, `.rows`, `.width`, `.multiline`, `.singleline`, `.auto_format`, `.large_number_rendering`, `.thousand_sep`, and `.decimal_sep`. They must handle truncation, grapheme clusters, readable suffixes and rounding for large numbers, alternate decimal/thousands separators, and row counts. With no argument, `.thousand_sep` writes `current thousand separator: ` followed by the current separator and a newline; the initial unset value is represented by a NUL byte. Likewise, no-argument `.decimal_sep` writes `current decimal separator: ` followed initially by a NUL byte and a newline. The magnitude of `.width` controls column width; its sign does not reverse the type-derived alignment, so `.width 8` and `.width -8` both render the numeric cell as `│    12 │`. `.headers`, `.nullvalue` (also `.null`), and `.separator` (also `.sep`) alter the applicable presentation settings. When duckbox truncates a result because of `.maxrows`, it retains the complete result as the special relation `_`; a following query such as `SELECT count(*) FROM _` can consume it, and `.last` rerenders that retained result without truncation. Ordinary untruncated results are not retained: `.last` after `SELECT 77` is a successful no-op, while querying `FROM _` exits 1 with `Binder Error: Failed to query last result "_": no result available`.

## Spec 5: Shell meta-commands

Recognize a dot command only in shell-command position, not when embedded in ordinary SQL. Implement:

- Introspection: `.help` (including patterns and `--all`), `.about`, `.databases`, `.tables [pattern]`, `.schema [pattern]`, `.schema -indent [pattern]`, `.schema --indent [pattern]`, `.indexes [table]`, `.show`, and `.version`. `.version` writes exactly `DuckDB v0.0.1 (Unknown Version) 780a7396` as its first line, followed by `gcc-11.4.0` as its second line. Both `-indent` and `--indent` are parsed as options rather than patterns and still emit matching CREATE statements, but this build does not pretty-print the result. After `CREATE TABLE test(id INT PRIMARY KEY, v VARCHAR NOT NULL)`, either `.schema -indent test` or `.schema --indent test` emits exactly the single line `CREATE TABLE test(id INTEGER PRIMARY KEY, v VARCHAR NOT NULL);;`: `INT` is canonicalized to `INTEGER`, and the output has two trailing semicolons followed by a newline. An ordinary `.schema` also canonicalizes an input `INT` column type to `INTEGER`; for example, a table created as `CREATE TABLE test_tbl (id INT, name VARCHAR)` is shown as `CREATE TABLE test_tbl(id INTEGER, "name" VARCHAR);`. Empty catalogs are handled without spurious data. Patterns, schema qualification, quoted names, views, many schemas/tables, and ambiguous names are handled in the DuckDB manner.
- Export/inspection: `.dump [table]` writes replayable SQL with transaction boundaries, schemas, tables, data, views, indexes, BLOB/string escaping, and quoted identifiers. `.sha3sum` is not implemented in this shell and reports `Unknown Command Error`; `.clone` is likewise unrecognized.
- Input and files: `.read FILE`, `.import [--csv|--parquet and CSV options] FILE TABLE`, `.open [options] FILE`, and `.cd DIRECTORY`. Import can create a table or append with casts; it autodetects CSV/TSV, supports explicit headers/delimiters, quoted and null fields, Unicode, empty and malformed input with ignore-errors behavior, and Parquet. Skip processing precedes header autodetection: when appending the three-line file `id,name,note\n1,Alice,"a,b"\n2,Bob,\n` with `--csv --skip 1`, the original header is skipped, the Alice record is then consumed as the inferred header, and only the Bob record is appended. A first ordinary import followed by that append therefore contains Alice once and Bob twice. A bare `.import` exits 1 and writes `ERROR: missing FILE argument. Usage:` followed by the ANSI-styled usage text to stdout, with empty stderr. `.import file.csv` behaves the same way except that its first line is `ERROR: missing TABLE argument. Usage:`.
- Output: `.output [FILE]` redirects subsequent results and truncates/overwrites the target as DuckDB does; omission restores stdout. In command-line `-c` processing, `.once FILE` has the same persistent lifetime: it redirects every subsequent result until an explicit `.output` with no filename restores stdout. Thus `.once FILE`, `SELECT 1`, `SELECT 2` writes both rows to `FILE` and nothing to stdout. `.print TEXT...`, `.log FILE|stdout|stderr|off`, `.pager`, and `.excel` follow normal shell behavior. Pager selection honors `DUCKDB_PAGER` before `PAGER`, accepts commands with arguments, and does not swallow errors.
- Session controls: `.mode`, `.headers`, `.nullvalue`, `.separator`, `.echo`, `.bail`, `.binary`, `.changes`, `.timer`, `.prompt`, `.highlight`, `.highlight_colors`, `.highlight_errors`, `.highlight_results`, `.highlight_mode`, `.render_completion`, `.render_errors`, `.progress_bar`, `.startup_text`, `.read_line_version`, `.ui_command`, `.display_colors`, `.shell`, `.system`, `.exit`, and `.quit`. `.edit` and `.pager` are also exposed by help. On/off settings take effect immediately. With `.timer on`, the timing line is appended to stdout after the result and begins `Run Time (s): real`; stderr remains empty for a successful query. `.changes on` is accepted but adds no affected-row output for `CREATE TABLE` or `INSERT`; creating a table and inserting three rows after enabling it leaves both stdout and stderr empty.

Missing arguments, nonexistent files, invalid patterns/modes/colors, malformed prompt escapes, and unknown dot commands yield useful errors rather than crashes. `.shell` and `.system` execute the requested host command only outside safe mode.

`.open --sql SQL` evaluates `SQL` against the current database and uses its result as the filename to reopen. The query must return exactly one row containing exactly one non-NULL column; that value is converted to the filename. The `--sql` option must have a query, may occur only once, and cannot be combined with a positional `FILE`. Violations exit 1 and write the applicable exact diagnostic to stderr: `Error: missing SQL query after --sql`, `Error: --sql provided multiple times`, `Error: cannot use both --sql and a FILE argument`, `Error: --sql query returned no rows, expected single value`, `Error: --sql query returned multiple rows, expected single value`, `Error: --sql query returned multiple columns, expected single value`, or `Error: --sql query returned a null value`. DDL and DML without a returned row take the no-rows path. If query evaluation itself fails, the stderr diagnostic begins `Error: failed to evaluate --sql query` and includes the underlying DuckDB error.

## Spec 6: Core SQL semantics

Implement DuckDB's SQL parser, binder, optimizer, and vectorized execution semantics for the following observable language:

- `SELECT`, aliases, quoted and case-insensitive identifiers, `VALUES`, expressions, scalar and correlated subqueries, `EXISTS`, `IN`/`NOT IN`, `ANY`/`ALL`/`SOME`, lateral queries, and arbitrary nesting.
- SQL `SHOW relation` returns a successful DESCRIBE-style result with the columns `column_name`, `column_type`, `null`, `key`, `default`, and `extra`; for `CREATE TABLE table1(mylittlecolumn INTEGER); SHOW table1`, its row describes `mylittlecolumn` as `INTEGER`. A top-level `CALL` can invoke a table function as a statement: `CALL range(4)` succeeds and returns the `range` column with rows `0`, `1`, `2`, and `3`.
- CREATE/DROP/ALTER for schemas, tables, temporary tables, columns, constraints, views, indexes, sequences, and macros where described below. INSERT (including multirow, defaults, SELECT, and RETURNING), UPDATE (FROM, CTE, subquery, expressions, and RETURNING), DELETE (USING, CTE, subquery, and RETURNING), and TRUNCATE.
- Inner, cross, left/right/full outer, natural, positional, lateral, ASOF, semi, and anti joins; `ON` and `USING`; equality and inequality/range conditions; null keys; duplicate keys; empty inputs; many-column and many-table joins. Optimizations must not change results, duplicate/remove rows incorrectly, reorder erroring expressions, or mishandle pushed filters, correlated/delim joins, generated columns, LIMIT/TOP-N, statistics, zonemaps, or projections.
- `UNION`, `INTERSECT`, and `EXCEPT`, each with distinct and `ALL` bag semantics, correct precedence, coercion, ordering/limits, NULL handling, and column-count errors.
- `ORDER BY` expressions, ordinals, aliases, multiple directions, collation, `NULLS FIRST/LAST`, `LIMIT` and `OFFSET`; negative values error. `DISTINCT`, `DISTINCT ON`, `QUALIFY`, and deterministic secondary ordering work as expected.
- `GROUP BY`, `GROUP BY ALL`, `HAVING`, aggregate `FILTER` and aggregate `ORDER BY`, `ROLLUP`, `CUBE`, `GROUPING SETS`, and `GROUPING()`.
- Recursive and nonrecursive CTEs, multiple/chained CTEs, recursive UNION deduplication, tree/graph traversal with cycle checks, deep recursion, recursive dates/strings/aggregates, and CTE use within DML, subqueries, joins, set operations, and windowed queries.
- `PIVOT`/`UNPIVOT`, including multiple aggregates, aliases, subqueries, NULL inclusion/exclusion, sparse and empty inputs, grouped sources, joins, ordering, filters, and validation errors.
- `USING SAMPLE` with reservoir, Bernoulli, and system methods; percentages and absolute row counts; `REPEATABLE` deterministic seeds; empty/zero/full/oversized samples; and composition with joins, filters, grouping, windows, CTEs, set operations, limits, and complex values.

SQL comments, multiple statements, semicolon handling, string/identifier escaping, operator precedence, and short-circuit behavior must be correct.

## Spec 7: Types, values, casts, and NULL

Support signed and unsigned integer widths through HUGEINT/UHUGEINT, DECIMAL with precision/scale, REAL/FLOAT/DOUBLE including infinities and NaNs, BOOLEAN, VARCHAR, BLOB, BIT, UUID, ENUM, DATE, TIME, TIME WITH TIME ZONE, TIMESTAMP precisions/time zones, INTERVAL, LIST/array (including fixed arrays), STRUCT, MAP, UNION, and VARIANT.

Implement literals, display, `typeof`/`pg_typeof`, comparison, hashing, grouping, ordering, storage, and explicit/implicit casts for these types. Complex values may nest arbitrarily (lists of structs, structs of lists, maps, nested lists, and variants), preserve field names and null/missing distinctions, and support field/key access, one-based and negative list indexes, slices, casts, unnesting, and aggregation. BLOB hex escapes and concatenation/base64/encoding round-trip correctly. BLOB values also support one-based inclusive bracket slices and `array_slice`: both `('abcdef'::BLOB)[2:4]` and `array_slice('abcdef'::BLOB, 2, 4)` produce the BLOB whose `hex` value is `626364`.

Use SQL three-valued logic throughout comparisons, boolean operators, CASE, joins, filters, HAVING, subqueries, set operations, DISTINCT/grouping, ordering, aggregates, windows, casts, strings, math, and temporal functions. `IS NULL`, `IS [NOT] DISTINCT FROM`, COALESCE, IFNULL, and NULLIF have DuckDB behavior. UNIQUE constraints allow multiple NULLs, while primary-key fields do not.

Casts enforce numeric bounds and validate date, time, timestamp, UUID, boolean, and nested-type input. `TRY_CAST` returns NULL instead of raising. Type combination/coercion in CASE, UNION, lists, arithmetic, and comparisons follows DuckDB. Diagnostics distinguish source and destination physical types, the offending value, and overflow versus malformed input.

## Spec 8: Expressions and built-in functions

Provide DuckDB behavior, overload resolution, aliases, NULL propagation, domain checking, and return types for:

- Conditional/general expressions: searched and simple CASE, IF, COALESCE, IFNULL, NULLIF, GREATEST/LEAST, BETWEEN, boolean tests, `constant_or_null`, `can_cast_implicitly`, and `stats`.
- Numeric operations: arithmetic and bitwise operators, integer division/modulo, ABS, SIGN, ROUND and round-even, FLOOR, CEIL, TRUNC, SQRT, CBRT, POW, EXP, LN/LOG/LOG2/LOG10, factorial, GCD/LCM, bit_count, EVEN, NEXTAFTER, trigonometric/hyperbolic functions, degrees/radians, `pi()`, formatted-byte parsing/rendering, RANDOM and SETSEED. Preserve decimal precision and detect integer overflow and invalid mathematical domains.
- Aggregates: COUNT, SUM (including booleans and overflow-safe wide accumulation), AVG, MIN/MAX, PRODUCT, BOOL_AND/OR, STRING_AGG, variance and standard deviation variants, covariance/correlation, median, mode, continuous/discrete percentiles, geometric mean, distinct/filter/order variants, and correct empty/all-NULL behavior.
- Strings: length/bit_length/ascii, upper/lower, Unicode-aware contains/prefix/suffix, LIKE/ILIKE with ESCAPE, regex match/extract/replace/split and options/groups/backreferences, substring/slicing, trim, pad, repeat, reverse, replace, translate, split_part, concat/concat_ws, position/instr, strip_accents, URL encoding, hex/base conversions, printf/format, edit/similarity distances, cryptographic hashes, and Unicode edge cases. `md5`, `sha1`, and `sha256` return lowercase hexadecimal digests; for `hello` they respectively return `5d41402abc4b2a76b9719d911017c592`, `aaf4c61ddcc5e8a2dabede0f3b482cd9aea9434d`, and `2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824`.
- Lists: construction (`[]`, `ARRAY[]`, `list_value`), concat, append/prepend, contains/position/extract/slice, sort/reverse/distinct/unique, flatten, resize/select/zip/grade-up, range/generate_series/generate_subscripts, set intersection/has-any/has-all, distances, scalar aggregates, `array_to_string`, and lambda transform/filter/reduce. A NULL separator to `array_to_string` selects a comma rather than propagating NULL: `array_to_string(['a','b','c'], NULL)` returns `a,b,c`. Accept both current lambda syntax and the tested deprecated forms. Validate incompatible lengths and empty reductions.
- Temporal operations: date/time/timestamp/interval arithmetic, DATE_ADD/DATE_DIFF/DATE_TRUNC/TIME_BUCKET, EXTRACT/DATE_PART, epoch conversions, MAKE_DATE/MAKE_TIME, STRFTIME/STRPTIME and try variants, LAST_DAY, AGE, month/day names, week/leap-year/month-boundary behavior, infinities/extreme dates, microsecond precision, and generated temporal series. Current/transaction timestamps are stable in the appropriate transaction scope.
- System functions: connection/query/transaction identifiers, `txid_current`, `current_query`, current catalog/schema/schemas/user/role, `current_setting`, `getenv`, UUID v4/v7 generation and UUID version/timestamp extraction, PostgreSQL-compatible size/time/schema/role helpers, `pg_sleep`, and an explicit `error()` function. `getenv` is disabled when external access is disabled.

## Spec 9: Windows, prepared statements, macros, and views

Window functions include ROW_NUMBER, RANK, DENSE_RANK, PERCENT_RANK, CUME_DIST, NTILE, LAG/LEAD with offsets/defaults and NULL handling, FIRST_VALUE/LAST_VALUE/NTH_VALUE, and aggregates used as windows. Support named/inline windows, multi-column partitioning and ordering, ROWS and RANGE frames, numeric RANGE offsets, unbounded/current-row bounds, and FILTER. They compose with CTEs, subqueries, DISTINCT results, grouping, and QUALIFY. Invalid frame ordering produces errors. A zero or negative constant second argument to `NTH_VALUE` is accepted and yields NULL for every row rather than a binder error; both `nth_value(i, 0)` and `nth_value(i, -1)` over `range(3)` produce three NULL rows and exit 0.

`PREPARE name AS ...`, `EXECUTE name(args...)`, and `DEALLOCATE` support SELECT and DML, numbered parameters, reuse, NULLs, implicit coercion, strings/dates/timestamps/arrays/booleans/doubles, expressions, aggregates, joins, subqueries, LIMIT, LIKE/IN/BETWEEN, and multiple independent statements. Numbered placeholders need not be contiguous at prepare time: `PREPARE p AS SELECT $1+$3` exits 0 with no output or diagnostic. Diagnose missing or excess arguments when executing, unknown statements, and conversion failures. Directly executing `SELECT ?` without bindings exits 1 and reports `Prepared statement parameters cannot be used directly`, followed by `To use prepared statement parameters, use PREPARE to prepare a statement, followed by EXECUTE`. Re-preparing an existing name replaces it as DuckDB does.

`CREATE MACRO`, `CREATE OR REPLACE MACRO`, `CREATE MACRO IF NOT EXISTS`, invocation, and DROP implement scalar expression macros with zero or many parameters, typed/default parameters, parameter scope, nested macro calls, list/struct/date/string/math expressions, subqueries/aggregates/EXISTS, and persistence. Duplicate, undefined, and wrong-arity calls error.

Views support CREATE, CREATE OR REPLACE, schema qualification, explicit column aliases, nesting, CTEs, correlated subqueries, joins, aggregates, windows, UNION, DISTINCT, LIMIT, HAVING, CASE, functions, and NULLs. Views dynamically reflect underlying data/schema changes where valid, persist to disk, and can be renamed/commented. Dropping an underlying table is not dependency-protected: `CREATE TABLE t(i INT); CREATE VIEW v AS SELECT * FROM t; DROP TABLE t` succeeds with no output. Querying the surviving view afterward exits 1 with `Catalog Error: Table with name t does not exist!`.

## Spec 10: Catalog objects, constraints, transactions, and storage

Indexes support single and multicolumn ART indexes, UNIQUE indexes, expression indexes where valid, schema qualification, IF NOT EXISTS, DROP IF EXISTS, persistence, NULLs, and the tested numeric/string/decimal/date/timestamp/boolean types. They enforce uniqueness without corrupting data; invalid columns/expressions, duplicate names, and dropping indexed columns are rejected.

Sequences support START, INCREMENT, MINVALUE, MAXVALUE, CYCLE, positive/negative ranges, schema-qualified and quoted names, `nextval`/`currval`, defaults, IF NOT EXISTS, OR REPLACE, DROP, and boundary errors. Sequence advancement has DuckDB's nontransactional behavior across rollback.

NOT NULL, UNIQUE, CHECK, PRIMARY KEY, and FOREIGN KEY constraints work for single/composite keys, temporary and persistent tables, INSERT and UPDATE, multiple constraints, NULL semantics, self-reference, and transactions. Foreign-key cascade syntax is not implemented and must be rejected as such.

Transactions support `BEGIN`, `BEGIN TRANSACTION`, `START TRANSACTION`, `COMMIT`, and `ROLLBACK`, explicit READ ONLY/READ WRITE modes, autocommit, DDL/DML atomicity, constraint errors, empty transactions, large operations, and repeated updates. Rollback restores tables, schema changes, indexes, and data. A transaction can write to only one attached database: after a transaction modifies the primary database, an attempted write to attached catalog `o` exits 1 with a `TransactionContext Error` ending `a single transaction can only write to a single attached database.` Cross-catalog reads remain supported.

Nested `BEGIN` and `COMMIT`/`ROLLBACK` without an active transaction exit 1 using the category `TransactionContext Error`, not `Transaction Error`. Their messages are respectively `cannot start a transaction within a transaction`, `cannot commit - no transaction is active`, and `cannot rollback - no transaction is active`. A constraint or execution error inside a transaction aborts that transaction. In a one-shot `-c` containing multiple semicolon-delimited statements, processing stops at that first error: subsequent SELECT, ROLLBACK, or other statements in the same command are not executed, so only the initial diagnostic is emitted. For example, a duplicate primary-key insert emits the `Constraint Error` and no later `Current transaction is aborted` message or result.

Persistent storage must correctly checkpoint and replay WAL for creates, drops, indexes, sequences, defaults, add/remove/rename/alter columns and tables/views, deletes, large/null/string updates, MAP/LIST/STRUCT/VARIANT values, failed commits, and lazy WAL creation. Reopening never exposes uncommitted changes. `CHECKPOINT`, automatic checkpoints, VACUUM, ANALYZE, storage statistics, and read-only WAL replay behave consistently.

VARIANT values work in memory, but a persistent VARIANT column requires storage version `v1.5.0` or later. Creating a VARIANT column, creating a table from a VARIANT expression, adding a VARIANT column, or altering a column to VARIANT in an earlier-format database exits 1 with an `Invalid Input Error` containing `VARIANT columns are not supported in storage versions prior to v1.5.0`. A disk database created with the default storage version therefore rejects these operations, while one created with `-storage-version v1.5.0` accepts them.

Storage supports configurable block sizes and the observable automatic/forced compression methods bitpacking, dictionary, FSST, RLE, roaring, and ZSTD; `PRAGMA storage_info` reports them consistently and scans/index fetches/filter pushdown return correct data. It also handles temp directories and swap limits, optimistic writes, repeated self-appends/deletes/checkpoints, backward-compatible supplied database files, and old views/internal schemas without corruption.

## Spec 11: Attached databases and file data

`ATTACH` and `DETACH` support disk and memory databases, aliases, READ_ONLY and TYPE/options syntax, IF NOT EXISTS, OR REPLACE, `USE`, multiple catalogs, catalog/schema-qualified references, cross-database joins/aggregates/views, information-schema visibility, and transaction commit/rollback. Aliases obey DuckDB case rules. Missing, duplicate, and nonattached targets produce catalog errors. An attached database can be modified when writable and later reopened independently.

Direct CSV access (`read_csv`, `read_csv_auto`, and filename-in-FROM shorthand), `glob`, filename/dirname parsing, and COPY FROM/TO support:

- headers/no headers, explicit column types, delimiter/quote/escape/null options, forced quoting, skip rows, ignore errors, BOM and Windows line endings;
- quoted delimiters/newlines, default empty-field-to-NULL conversion, mixed quoting/types, Unicode, very long rows, all-NULL columns, temporal inference, column reordering with `union_by_name`, filename columns, multi-file globs, and gzip CSV. In particular, `COPY ... TO` with `FORCE_QUOTE` writes an empty string as `""` and NULL as an unquoted empty field, but a default `COPY ... FROM ... (HEADER)` reads both back as NULL; a round trip of `(1,'a,b'),(2,''),(3,NULL)` therefore renders the latter two values identically after `coalesce(s,'<null>')`;
- export of tables or queries, selections/joins, empty tables, large data, numeric and temporal precision, special characters, overwrite behavior, stdout/stderr, and gzip output;
- Parquet read/import and data/type-preserving Parquet round trips.

Missing input and nonexistent output directories yield IO errors. File access obeys `enable_external_access` and safe mode. Local `file://` handling follows DuckDB rules. A NULL expression used as the path-list argument is an error rather than an empty set: `read_csv_auto(NULL)` exits 1 with `Parser Error: read_csv_auto cannot take NULL list as parameter`, and `glob(NULL)` exits 1 with `Parser Error: glob cannot take NULL list as parameter`. The same applies when the NULL is returned by `getvariable`.

`EXPORT DATABASE 'DIRECTORY'` creates an export that preserves table definitions and rows, and `IMPORT DATABASE 'DIRECTORY'` restores them when these operations are submitted as separate command sources. For example, when creation, export, dropping, import, and selection are supplied through successive `-c` options, exporting tables containing `range(100)` and the rows `(1), (3), (99)`, dropping both tables, and importing the directory makes `SELECT SUM(i)*MAX(i) FROM integers JOIN integers2 USING (i);` return `10197`. This build behaves differently when that entire sequence is one semicolon-delimited `-c` command: it exits 1, leaves no export directory, and writes `IO Error: Cannot open file "DIRECTORY/schema.sql": No such file or directory` to stderr, with no stdout.

## Spec 12: Metadata, settings, plans, extensions, and geometry

Implement `DESCRIBE`, `SHOW TABLES`, `SHOW DATABASES`, `SHOW SCHEMAS`, information_schema tables/columns/schemata, and DuckDB catalog table functions including `duckdb_tables`, `duckdb_columns`, `duckdb_schemas`, `duckdb_databases`, `duckdb_views`, `duckdb_functions`, `duckdb_settings`, `duckdb_extensions`, `duckdb_constraints`, `duckdb_indexes`, `duckdb_keywords`, `duckdb_sequences`, and `duckdb_triggers`. Their columns, logical types, ordering when requested, SQL definitions, comments/defaults, nullability, numeric precision/scale, constraint counts, primary-key flags, temporary/internal flags, extension aliases/status, and identifier case must match the actual catalog. `duckdb_triggers()` exists and is empty initially.

Support relevant PRAGMAs and equivalent `SET`/`current_setting` behavior for threads, memory limit, profiling, optimizer and verification toggles, explain output, null/default ordering, search path/schema, temp and home directories, external access/object cache/macro dependencies/view dependencies, checkpoint threshold, insertion order, integer division, expression depth, warnings-as-errors, debug external/no-cross-product controls, extension repository/directory/autoload settings, and configuration locking. `SET` accepts evaluated scalar expressions rather than only literals: `SET threads = concat('2',''); SELECT current_setting('threads')` succeeds and returns `2`. Validate names, ranges, and size formats. `ordered_aggregate_threshold` must be positive: setting it to `0` exits 1 with `Parser Error: Invalid option for PRAGMA ordered_aggregate_threshold, value must be positive`. `allowed_configs` is a list-valued exception to configuration locking: after `SET allowed_configs=['max_expression_depth']; SET lock_configuration=true`, setting `max_expression_depth=50` succeeds and `current_setting('max_expression_depth')` returns `50`. Profiling supports text and JSON output and optimizer-detail modes.

The catalog table function `duckdb_connection_count()` returns one row with a `count` column containing the number of current connections; in a fresh command-line invocation, `SELECT * FROM duckdb_connection_count()` returns `1`.

`EXPLAIN`, `EXPLAIN ANALYZE`, and text/JSON formats produce nonempty valid plans with the applicable operators, join types/conditions, projections, filters, cardinality/timing information, and JSON structure for SELECT, DML, aggregation, ordering/TOP-N, CTEs, subqueries, set operations, and windows. Invalid references still fail during explain.

The extension SQL surface supports `INSTALL`, `FORCE INSTALL`, `LOAD`, version and custom repository clauses, aliases/case normalization, and the extension catalog/settings. Failed downloads report HTTP status, constructed URL, candidate extensions where applicable, and a troubleshooting URL. Reject malformed syntax, nonexistent paths, traversal/invalid suffixes, directories, files smaller than 512 bytes, and invalid signatures with specific Parser/IO/Invalid Input errors. `-unsigned` enables unsigned extensions at startup; changing that security option after startup is rejected. Do not execute shell interpolation embedded in repository URLs or names.

Known extension-owned SQL types such as JSON and INET are not silently present in the base catalog. When referenced without their extension, the catalog error identifies the owning extension and suggests `INSTALL` and `LOAD`; failed installation/loading then follows the versioned URL and local-path behavior above. This is independent of the built-in CLI `-json` result renderer.

Remote filesystem access is likewise owned by the `httpfs` extension. Without it loaded, a `COPY ... TO` target or `read_blob` input using an HTTPS or S3 URI exits 1 rather than silently succeeding or reporting a generic IO error. For example, copying to the probed HTTPS target begins `Missing Extension Error: File https://example.com/spec004.csv requires the extension httpfs to be loaded`; reading the corresponding remote BLOB begins `Missing Extension Error: File https://example.com/spec004.bin requires the extension httpfs to be loaded`. The diagnostic then suggests `INSTALL httpfs;`, `LOAD httpfs;`, and the known-extension auto-install/auto-load settings. For `read_blob`, it is followed by the SQL `LINE 1:` excerpt and caret.

The `TimeZone` setting is likewise owned by the ICU extension and is unavailable in the base catalog. Without ICU loaded, `SET TimeZone='ECT';` exits 1 with a `Catalog Error` stating `Setting with name "TimeZone" is not in the catalog, but it exists in the icu extension.` and then suggests installing/loading ICU or enabling known-extension auto-install and auto-load.

GEOMETRY is available with DuckDB's native casts and rendering for POINT, LINESTRING, POLYGON (including holes), MULTI* types, and GEOMETRYCOLLECTION, including EMPTY, Z, M, and ZM forms, NULLs, negative/zero/large/high-precision coordinates, and nested collections. Provide `ST_AsText`, `ST_AsWKB`, `ST_GeomFromWKB`, bounding-box `&&`, `ST_Intersects_Extent`, and CRS inspection. WKT/WKB round trips preserve shape and dimensions. Invalid type names produce conversion errors, while an incomplete coordinate such as `'POINT (1)'::GEOMETRY` exits 1 with `Invalid Input Error: Expected number at position 8`.

Trigger execution is intentionally unavailable in the base executable. Without the harness-provided autocomplete parser extension, `CREATE TRIGGER` fails at `TRIGGER` with a parser error and line/caret context. `DROP TRIGGER x` is a distinct end-of-input case: it exits 1 and its entire diagnostic is `Parser Error: syntax error at end of input` followed by a newline, with no SQL excerpt or caret. `CALL enable_peg_parser()` is a catalog error explaining that the function belongs to the autocomplete extension.

## Spec 13: Diagnostics

Errors go to stderr and successful result data to stdout, except explicitly redirected shell output and diagnostic/profiling streams and the missing-argument `.import` usage errors described in Spec 5, which go to stdout. Diagnostics use DuckDB categories such as `Parser Error`, `Binder Error`, `Catalog Error`, `Conversion Error`, `Constraint Error`, `Transaction Error`, `IO Error`, `Invalid Input Error`, `Out of Range Error`, and `HTTP Error`. With `errors_as_json=true`, an SQL error is instead one compact JSON object on stderr. For `SET errors_as_json=true; SELECT * FROM missing_table`, it has `exception_type` equal to `Catalog`, an `exception_message` containing the missing-table message, `candidates` equal to `pg_tables`, string-valued `position` equal to `39`, `error_subtype` equal to `MISSING_ENTRY`, `type` equal to `Table`, and `name` equal to `missing_table`; the invocation exits 1.

Messages include useful object/value/type details. SQL diagnostics that identify a source position include the original `LINE n:` excerpt plus a caret under the relevant token, but the `DROP TRIGGER x` end-of-input parser error described in Spec 12 is an observed exception and contains neither. Binder diagnostics offer candidate columns/functions and qualified references when useful; missing catalogs/tables/functions offer close suggestions or identify a known-but-unloaded extension; constraint diagnostics identify the violated key/expression; regex/date/time/format errors describe the invalid pattern or unit. Error rendering remains correct for long input, single/double quotes, multiline SQL, Unicode, and NUL bytes. Ordinary user errors exit nonzero without stack traces, assertions, or partial unintended changes. The status-0 exceptions are the invalid `-storage-version` metadata path described in Spec 3 and both unavailable-autocomplete formatting paths described in Spec 2; `-format-file` still writes its catalog diagnostic despite that successful status.

Warnings are rendered separately from errors but not on a separate stream from successful results. Deprecated lambda arrow syntax still executes and emits one ANSI-styled warning block per statement to stdout before that statement's result; stderr remains empty. Multiple deprecated arrows in one statement still produce only one block. Its visible layout is exactly:

```text
WARNING:
Deprecated lambda arrow (->) detected. Please transition to the new lambda syntax, i.e.., lambda x, i: x + i, before DuckDB's next release.
Use SET lambda_syntax='ENABLE_SINGLE_ARROW' to revert to the deprecated behavior.
For more information, see https://duckdb.org/docs/current/sql/functions/lambda.html.

```

The label occupies its own line rather than forming the contiguous phrase `WARNING: Deprecated`. In the byte stream, `WARNING:\n` is preceded by `\x1b[90m`; the message is preceded by `\x1b[00m\x1b[90m`; and the blank line is followed by `\x1b[00m` immediately before result output. With `warnings_as_errors=true` the same condition is an error and the process exits unsuccessfully. Configured logging can emit severity-prefixed `TRACE:`, `INFO:`, and related records without corrupting query results.
