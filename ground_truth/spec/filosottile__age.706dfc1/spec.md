# Clarified specification for `executable`

This document specifies the complete observable contract of the required artifact. The artifact is a single executable file named exactly `executable`; it implements the `age` command-line encryption/decryption program described below. The evaluation harness provides auxiliary programs such as `age-keygen`, `age-inspect`, `age-plugin-batchpass`, `ssh-keygen`, and test plugins. Those programs are not part of the artifact and their user interfaces are not requirements here, but `executable` must interoperate with the keys, encrypted files, and plugin protocol they provide.

In this document, “raw Base64” means the standard `+/` Base64 alphabet with no `=` padding, “strict Base64” means unused trailing bits must be zero, HKDF means HKDF-SHA-256, and AEAD means ChaCha20-Poly1305 with a 32-byte key, 12-byte nonce, 16-byte authentication tag, and no associated data unless stated otherwise. All random values must come from a cryptographically secure source.

## Spec 1

The artifact must be a regular executable at `./executable`. It is invoked as `age` for purposes of usage and diagnostic text. It must accept arbitrary binary input and produce arbitrary binary output without text conversion, including empty input, NUL bytes, every byte value, Unicode text encoded as bytes, and files containing very long lines. A successful complete encryption or decryption exits 0. Usage, parse, I/O, authentication, or cryptographic failures exit 1 (any nonzero status is acceptable where a test only requires failure), write a useful diagnostic to standard error, and must not report success. Normal ciphertext/plaintext goes only to standard output or the selected output file; diagnostics and warnings go only to standard error.

The implementation must be stateless between invocations. Repeated encryptions of identical plaintext to the same recipient must produce different ciphertext because fresh file keys, wrapping randomness, salts, and payload nonces are used. It must support many sequential invocations without leaked child processes or file descriptors.

## Spec 2

The accepted command forms are:

```text
age [--encrypt] (-r RECIPIENT | -R PATH)... [--armor] [-o OUTPUT] [INPUT]
age [--encrypt] --passphrase [--armor] [-o OUTPUT] [INPUT]
age --encrypt (-i PATH | -j PLUGIN)... (-r RECIPIENT | -R PATH)* [--armor] [-o OUTPUT] [INPUT]
age --decrypt [-i PATH | -j PLUGIN]... [-o OUTPUT] [INPUT]
```

Options and aliases are `-e`/`--encrypt`, `-d`/`--decrypt`, `-o`/`--output`, `-a`/`--armor`, `-p`/`--passphrase`, `-r`/`--recipient`, `-R`/`--recipients-file`, `-i`/`--identity`, `-j PLUGIN`, and `-h`/`-help`/`--help`. The value-taking long options may accept either a following argument or `--name=value`. Encryption is the default when `-d` is absent; an invocation without any recipient/passphrase mechanism therefore reaches the `missing recipients` error. Using `-i` or `-j` for encryption requires an explicit `-e`. Options must precede the one optional positional `INPUT`.

With no arguments, print usage to standard error and exit 1. Any help option prints complete usage to standard error, nothing to standard output, and exits 0 even when preceded by otherwise incomplete flags such as `-p`. Usage must mention all modes and principal options. An unknown option prints an error containing `flag provided but not defined` plus usage and exits nonzero.

## Spec 3

Reject invalid option combinations before processing data. Diagnostics must contain the quoted core text below and, where shown, the hint on a separate `age: hint:` line:

- Both encryption and decryption: `-e/--encrypt can't be used with -d/--decrypt`.
- `-a` with decryption: `-a/--armor can't be used with -d/--decrypt`; hint `note that armored files are detected automatically, try again without -a/--armor`.
- `-p` with decryption: `-p/--passphrase can't be used with -d/--decrypt`; hint `note that password protected files are detected automatically`.
- `-r` or `-R` with decryption: respectively `-r/--recipient can't be used with -d/--decrypt` or `-R/--recipients-file can't be used with -d/--decrypt`; hint `did you mean to use -i/--identity to specify a private key?`.
- `-p` combined with `-r`: `-p/--passphrase can't be combined with -r/--recipient`.
- `-p` combined with `-R`: `-p/--passphrase can't be combined with -R/--recipients-file`.
- For `-p -i PATH` or `-p -j PLUGIN` without explicit `-e`, the explicit-encryption check takes precedence: report `-i/--identity and -j can't be used in encryption mode unless symmetric encryption is explicitly selected with -e/--encrypt` and hint `did you forget to specify -d/--decrypt?`. With explicit `-e`, report `-p/--passphrase can't be combined with -i/--identity and -j`.
- Encryption with `-i` or `-j` but without explicit `-e`: `-i/--identity and -j can't be used in encryption mode unless symmetric encryption is explicitly selected with -e/--encrypt`.
- Encryption with no recipient mechanism: `missing recipients`; hint `did you forget to specify -r/--recipient, -R/--recipients-file or -p/--passphrase?`.

At most one positional input is accepted. Multiple inputs produce `too many INPUT arguments`. For ordinary multiple positional inputs, add the separate hint `only a single input file may be specified at a time`. If the likely cause is an input placed before later flags, add `the input file must be specified after all flags`; for arguments containing only shell-safe characters, also show `did you mean:` and a corrected command with flags before input. Do not produce a command suggestion for names containing spaces or other shell-unsafe characters.

## Spec 4

Absent `INPUT` means read standard input. A positional `-` also denotes standard input. Absent `-o` means standard output; `-o -` explicitly means standard output. A named input must be opened read-only, and open failures must mention `failed to open input file`, the requested path, and the operating-system cause. For a nonexistent named input, that cause contains the case-sensitive lowercase text `no such file or directory`. A named output is created only when the operation is ready to write; errors discovered while opening input, parsing recipients/identities, selecting identities, or preparing encryption must leave a previously nonexistent output absent. Existing output files are overwritten on successful operations, and a successful operation producing empty plaintext still creates or truncates its selected output file. Parent directories are not created automatically, but deeply nested already-existing paths and filenames containing spaces or Unicode must work.

Resolve input and output sufficiently to detect the same file even through relative/absolute spellings; reject it with `input and output file are the same: "PATH"` before truncating it. Flush and close output and propagate errors from write or close. If encrypting unarmored binary to an actual terminal and output was only implicitly selected, refuse with `refusing to output binary to the terminal`, hint `did you mean to use -a/--armor?`, and hint `force anyway with "-o -"`. Explicit `-o -` permits it.

A single standard-input stream cannot simultaneously be plaintext/ciphertext input and a `-R -` recipients file or `-i -` identity file. Reject such conflicts with `standard input is used for multiple purposes`. Reading recipients or identities from `-` is valid when a separate named input file was supplied.

## Spec 5

User-facing failures have this shape:

```text
age: error: DESCRIPTION
age: hint: OPTIONAL HINT
age: report unexpected or unhelpful errors at https://filippo.io/age/report
```

Warnings use `age: warning: DESCRIPTION` and do not make an otherwise successful operation fail. Except for the case-sensitive operating-system substrings explicitly required in this document, exact low-level operating-system wording can vary; paths, line numbers, recipient text, and all explicitly required diagnostic substrings must be retained. Do not emit a report line for success. For ordinary successful encryption/decryption without a warning or interactive prompt, standard error is empty.

Malformed CRLF-redirection input beginning `age-encryption.org/v1\r\n`, and UTF-16LE/BOM-like encodings of the same intro, receive the specialized error `invalid header intro`, plus hints `it looks like this file was corrupted by PowerShell redirection` and `consider using -o or -a to encrypt files in PowerShell`.

## Spec 6

`-r` accepts one recipient string per occurrence and is repeatable. `-R` reads a UTF-8 recipient file containing one entry per line and is repeatable and combinable with `-r` and encryption-mode `-i`. Blank lines and lines whose first byte is `#` are ignored; Unicode is allowed in comment text. CRLF line endings are accepted. Recipient lines themselves are not trimmed: leading/trailing spaces, an inline ` # comment`, or otherwise extra text is part of the value and normally makes it malformed, except that authorized-keys SSH syntax permits its own whitespace-separated comment. Tab-separated valid SSH public-key fields are accepted.

Reject a non-UTF-8 file with `recipients file is not valid UTF-8`; reject a physical non-comment recipient line longer than 8 KiB (8,192 bytes) with `line N is too long`; reject an empty/comment-only file with `no recipients found`. A malformed entry is reported as `malformed recipient at line N`, while a secret-key-looking entry is `error at line N: apparent identity found in recipients file`. Wrap all recipient-file loading failures with `failed to parse recipient file "PATH"` and include the path. This wrapper also applies when the file cannot be opened: a missing file includes the nested text `failed to open recipient file`, retains the requested path, and contains the case-sensitive lowercase operating-system text `no such file or directory`. Accept long comment lines near 8 KiB, handle at least 1,500 recipients, and cap the overall recipient file at 16 MiB.

Valid but unsupported SSH public-key algorithms found in a recipient file are skipped if at least one supported recipient remains, with `age: warning: recipients file "PATH": ignoring unsupported SSH key of type "TYPE" at line N`. An unsupported SSH key passed directly to `-r` is an error. If skipping leaves no recipients, fail.

## Spec 7

`-i PATH` is repeatable. A normal textual identity file is strict UTF-8 with one identity per line; ignore blank lines and lines beginning `#`, accept CRLF, and try all identities across all supplied files. Do not require every identity to be used. Reject invalid UTF-8 with `identities file is not valid UTF-8`, empty/comment-only content with `no identities found`, a public-recipient-looking line with `error at line N: apparent recipient found in identities file`, and unknown or malformed secret lines with `error at line N: unknown identity type` or the underlying `malformed secret key` reason. Diagnostics include `reading "PATH": failed to read "PATH"` and the path. A nonexistent identity must mention `failed to open file` and its path.

In decryption mode, opening, reading, and validating explicitly supplied `-i` identity files precedes parsing the ciphertext header. An identity-file open or content error therefore takes precedence over a simultaneous malformed ciphertext error: with input such as `test` or `dummy encrypted content`, report the applicable `failed to open file`, `no identities found`, apparent-recipient, line-numbered unknown-identity, invalid-UTF-8, or `malformed secret key` error instead of `unexpected intro`.

A `-i` file may instead be one whole unencrypted SSH private key, or an age-encrypted/armored identity file as detailed later. A single identity file can contain multiple classic or hybrid native identities, and every one is tried. In explicit encryption mode (`-e -i PATH`), derive the corresponding public recipient from each identity and encrypt to it; this may be combined with direct recipients. Plugin identity encodings in identity files must be recognized and dispatched to their plugin, not treated as unknown text.

## Spec 8

Native strings use modified BIP-173 Bech32. Split at the last `1`, require a nonempty HRP and at least six checksum symbols, reject mixed case, require printable ASCII HRP, and map the data characters through `qpzry9x8gf2tvdw0s3jn54khce6mua7l`. For checksum verification, lowercase the HRP and expand it to every character shifted right five bits, then zero, then every character masked with 31; append all mapped data including the six checksum symbols. Starting `chk=1`, for each five-bit value set `top=chk>>25`, set `chk=((chk & 0x1ffffff)<<5) XOR value`, and XOR generator `i` when bit `i` of `top` is set. The generators are `3b6a57b2,26508e6d,1ea119fa,3d4233dd,2a1462b3`, and the final value must equal 1. Remove the checksum and convert 5-bit groups to 8-bit bytes, most-significant-bit first, without nonzero or excessive padding. To encode, convert 8-bit bytes to 5-bit groups with zero padding, append six zero groups, compute the same polymod XOR 1, and replace the six groups by its six big-endian five-bit pieces. Emit the whole string lowercase for a lowercase HRP or uppercase for an uppercase HRP. Report failures such as `invalid character data part`, `invalid checksum`, etc.

Classic X25519 recipients have lowercase HRP `age` and exactly 32 decoded bytes, conventionally 62 characters total and beginning `age1`. Their identities have uppercase HRP `AGE-SECRET-KEY-`, exactly 32 decoded bytes, and begin `AGE-SECRET-KEY-1`. Hybrid recipients have lowercase HRP `age1pq` (therefore begin `age1pq1`) and contain an ML-KEM-768-X25519 HPKE public key. Hybrid identities have uppercase HRP `AGE-SECRET-KEY-PQ-` and begin `AGE-SECRET-KEY-PQ-1`; their decoded form is the corresponding HPKE private key. Enforce HRP, decoded length/algorithm validity, character set, checksum, and case after a string has been dispatched to one of these decoders. Recognizing public native recipients is itself case-sensitive: a value beginning `AGE1`, including `AGE1QQQQQQ`, or a value with an uppercased/mixed-case prefix is not dispatched to the native decoder and instead reports `unknown recipient type: "VALUE"`. For a recognized lowercase native prefix, recipient decoding failures take the form `malformed recipient "VALUE": REASON`; secret failures take `malformed secret key: REASON`.

Recipient parsing gives reserved prefixes priority: `age1pq1` must be parsed as hybrid, and `age1tag1`/`age1tagpq1` as tags, so malformed reserved encodings cannot silently fall through. For any other string beginning `age1`, first try the fixed-size native X25519 form and then the plugin grammar of Spec 21; if the latter is structurally plugin-like but malformed, report `invalid recipient encoding: REASON`. In particular, `age1notpqkey123456789abcdef` reports `invalid recipient encoding: invalid character data part: s[9]=98`. A string not matching a supported native, SSH, tag, or plugin syntax yields `unknown recipient type: "VALUE"`.

The obsolete syntax `github:USERNAME` must fail with `"github:" recipients were removed from the design` and hints showing both `curl -O https://github.com/USERNAME.keys` and `age -R USERNAME.keys`.

## Spec 9

The binary age v1 file is a byte concatenation of a textual header, a 16-byte random payload nonce, and an authenticated chunk stream. The header grammar is:

```text
age-encryption.org/v1\n
-> TYPE [ARG ...]\n
RAW-BASE64-STANZA-BODY-WRAPPED-AT-64-COLUMNS\n
[additional stanzas]
--- RAW-BASE64-OF-32-BYTE-HEADER-MAC\n
```

There is no blank separator. `TYPE` and each `ARG` are nonempty ASCII bytes 33 through 126 and separated by exactly one ASCII space. Stanza bodies use strict raw Base64, lines decode to at most 48 bytes, and a body must end with a line decoding to fewer than 48 bytes. Consequently a body whose encoding ends on a 64-character boundary is followed by an empty line. The writer never emits `=` in stanza bodies or the MAC. Stanzas appear in recipient-option order (including entries expanded in file order), except that one plugin recipient may itself return multiple stanzas.

To parse, require the intro including LF exactly. Empty input reports `file is empty`; another intro reports the escaped offending line with one literal backslash before the newline marker, for example `failed to read header: parsing age header: unexpected intro: "bad-header\n"`. Require a newline on every header line. If EOF occurs where the next stanza or closing line is expected, report `failed to read header: parsing age header: failed to read header: EOF`. If it instead occurs after an unterminated stanza opening such as `-> X25519`, report `failed to read header: failed to parse header: failed to read line: EOF`; this takes precedence over the separate `stanza ended without a short line` condition for a stanza whose opening and body lines were read. The closing line has exactly one argument which strictly decodes to 32 bytes. Reject missing/truncated lines, malformed stanza openings, empty/control/non-ASCII arguments, invalid raw Base64, body lines over 64 encoded columns/48 decoded bytes, a body ending without a short line, and malformed/multiple/incorrect-length closing arguments. Preserve buffered bytes after the closing LF exactly as payload bytes.

Malformed header diagnostics quote the complete offending raw line with control bytes and the LF escaped. Empty stanza type, a control byte in an argument, and no arguments respectively report `failed to read header: failed to parse header: malformed stanza: "->  arg1\n"`, `failed to read header: failed to parse header: malformed stanza: "-> X25519 test\x01arg\n"`, and `failed to read header: failed to parse header: malformed stanza: "-> \n"`. Strict Base64 decoding precedes the decoded-length check: a 65-character `A` body line reports `malformed body line "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA\n": illegal base64 data at input byte 64`, while a 100-character `A` line reports `malformed body line "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA\n": too long`. The invalid line `ABC\n` reports `failed to read header: failed to parse header: parsing age header: malformed body line "ABC\n": illegal base64 data at input byte 2`. An incorrect-length footer `--- dGVzdA\n` reports `failed to read header: parsing age header: malformed closing line "--- dGVzdA\n": <nil>`, while `--- MAC1 MAC2\n` reports `failed to read header: parsing age header: malformed closing line: "--- MAC1 MAC2\n"`. Other relevant diagnostics include `stanza ended without a short line`.

## Spec 10

For every encryption generate an independent uniformly random 16-byte file key. After all recipient stanzas are marshaled, derive `macKey = HKDF(fileKey, salt=empty, info="header", length=32)`. The header MAC is HMAC-SHA-256 under `macKey` over the exact serialization from the intro through all stanza bodies and through the three bytes `---`, but excluding the space, encoded MAC, and final LF. Compare it in constant time on decryption and fail with exactly `bad header MAC` on mismatch.

Generate an independent random 16-byte payload nonce, append it immediately after the header LF, and derive `payloadKey = HKDF(fileKey, salt=payloadNonce, info="payload", length=32)`. Fewer than 16 payload-nonce bytes is an error containing `failed to read nonce`. This common envelope is used for X25519, SSH, hybrid, tag, scrypt, and plugin-produced stanzas, so every supported recipient ultimately unwraps the same 16-byte file key.

## Spec 11

Encrypt plaintext with ChaCha20-Poly1305 under `payloadKey` in chunks of at most 65,536 bytes. The 12-byte chunk nonce consists of an 88-bit big-endian counter in bytes 0–10, initially zero, and a final-chunk flag in byte 11. Nonfinal chunks use flag 0; the final chunk uses flag 1. Increment the 88-bit counter after each chunk. There is no associated data. Every chunk appends a 16-byte AEAD tag. Empty plaintext is represented by one final empty plaintext chunk (16 ciphertext bytes). An exact multiple of 65,536 bytes marks its last full-sized chunk final and does not add another empty chunk.

On decryption, authenticate before releasing each chunk. A short ciphertext chunk is necessarily final and uses flag 1. For a full-sized encrypted chunk (65,552 bytes), first try the nonfinal nonce and, if authentication fails, try the final flag; once a final full chunk succeeds, require immediate EOF. EOF without a marked final chunk is truncation. After authenticating and releasing a full nonfinal 65,536-byte plaintext chunk, such EOF exits 1 with `unexpected EOF`. Reject a noninitial empty final chunk; after releasing the preceding authenticated full chunk, this exits 1 with `last chunk is empty, try age v1.0.0, and please consider reporting this`. Other tag failures or corrupt ciphertext report `failed to decrypt and authenticate payload chunk, file may be corrupted or tampered with`; bytes after a valid full final chunk report `trailing data after end of encrypted file`. Never output unauthenticated bytes, although these two termination failures have already released the preceding authenticated chunk. Correct behavior is required immediately below, at, and above all chunk boundaries, for many chunks, and for at least 100 MiB streams.

## Spec 12

For an X25519 recipient, choose a fresh 32-byte ephemeral scalar, compute ephemeral public point `E = X25519(e, basepoint)` and shared secret `S = X25519(e, recipientPublic)`, rejecting invalid/all-zero results. Derive `wrapKey = HKDF(S, salt=E || recipientPublic, info="age-encryption.org/v1/X25519", length=32)`. Encrypt the 16-byte file key with AEAD under `wrapKey`, all-zero 12-byte nonce, no associated data. Emit one stanza with type `X25519`, one raw-Base64 argument containing the 32-byte `E`, and a 32-byte body (file key plus tag).

To unwrap, require exactly one argument decoding to 32 bytes and exactly a 32-byte body. Compute the identity public point from its scalar; use salt `E || identityPublic` and the same derivation/AEAD operation. Authentication failure means that identity does not match, so other identities/stanzas are tried. This format must decrypt the supplied fixed v1 files and files made by the harness, and ciphertext it creates must decrypt with harness-generated identities.

## Spec 13

Support OpenSSH `ssh-ed25519` and `ssh-rsa` public recipients in authorized_keys form, supplied inline or in recipient files. A line consists of the ASCII algorithm name, whitespace, padded standard Base64 of an SSH wire blob, and an optional whitespace/comment suffix that is ignored for cryptography. Every SSH wire `string` is a four-byte unsigned big-endian length followed by that many bytes. An Ed25519 blob is `string("ssh-ed25519") || string(32-byte-public-key)`. An RSA blob is `string("ssh-rsa") || mpint(e) || mpint(n)`, where an `mpint` has the same length prefix and a big-endian two's-complement payload (these public values must be positive; a leading zero protects a high sign bit). Consume the blob exactly. When the outer token is one of the two supported algorithms but disagrees with the algorithm embedded in a valid blob, trust the embedded algorithm: for example, `ssh-rsa ` followed by a valid Ed25519 blob is accepted, encryption exits 0 with empty standard error, and the emitted stanza type is `ssh-ed25519`. Other malformed encodings report `malformed SSH recipient` and retain causes such as `illegal base64 data`. Direct algorithms other than the two supported ones fail with `unknown SSH recipient type: "TYPE"`. RSA modulus size must be at least 2048 bits. A smaller RSA key supplied directly with `-r` fails with `RSA key size is too small`; when the same valid but too-small key occurs in a recipients file, treat it as an unsupported SSH key under Spec 6, warn with type `ssh-rsa` and its line number, skip it, and continue if another supported recipient remains.

For both SSH forms, compute the visible fingerprint argument as the first four bytes of SHA-256 over the SSH public-key wire encoding, raw-Base64 encoded. This deliberately makes SSH recipient stanzas linkable to the key.

For RSA, stanza type is `ssh-rsa`, its sole argument is the fingerprint, and its body is RSA-OAEP-SHA-256 encryption of the 16-byte file key with label `age-encryption.org/v1/ssh-rsa`.

For Ed25519, do not require the compressed Edwards public-point encoding to be canonical before conversion. Obtain its little-endian `y` after clearing the sign bit, and convert it to the Curve25519 Montgomery coordinate `u=(1+y)/(1-y) mod p` for `p=2^255-19`, serialized little-endian. In particular, a wire-valid `ssh-ed25519` blob whose 32-byte public value consists entirely of `0xff` bytes is accepted: encryption exits 0, emits ciphertext, and writes nothing to standard error. Generate an ephemeral X25519 pair `e,E` and compute `S = X25519(e, convertedPublic)`. Derive 32-byte `tweak = HKDF(input=empty, salt=SSH-wire-public-key, info="age-encryption.org/v1/ssh-ed25519")`, then replace `S` by `X25519(tweak,S)`. Derive `wrapKey = HKDF(S, salt=E || convertedPublic, info="age-encryption.org/v1/ssh-ed25519", length=32)` and wrap the file key using AEAD with all-zero nonce. Emit type `ssh-ed25519`, arguments `fingerprint` and raw-Base64 `E`, and the 32-byte wrapped-key body. To unwrap, hash the 32-byte Ed25519 private seed with SHA-512, clamp the first 32 digest bytes as an X25519 scalar (`b[0]&=248; b[31]&=127; b[31]|=64`), compute X25519 with `E`, then apply X25519 with `tweak` before the wrap-key derivation. Require the fingerprint to match before private-key work.

## Spec 14

`-i` accepts unencrypted RSA and Ed25519 private keys in modern OpenSSH, PKCS#1, and PKCS#8/PEM forms and derives the recipients described above. It must accept 2048- and 4096-bit RSA keys and Ed25519 keys, including PKCS#8 Ed25519. DSA and other private-key types are unsupported. An incorrect key is a nonmatch, not plaintext output.

For passphrase-protected SSH private keys, obtain the public key without prompting when possible (embedded OpenSSH public portion or a corresponding `PATH.pub`). Compare its type/fingerprint with all stanzas first. If it does not match, return the normal no-match error without asking for a password. Only a matching key may trigger a terminal prompt. With no terminal, both encrypted Ed25519 and RSA OpenSSH keys report exactly `failed to obtain passphrase: could not read passphrase for "PATH": standard input is not a terminal, and /dev/tty is not available: open /dev/tty: no such device or address`, followed by the standard report line. For encrypted legacy PEM or a key supplied through `-i -`, when no public portion can be obtained, fail with `failed to obtain public key for "PATH" SSH key`. For a named legacy PEM path, leave a blank line after that error and emit the unprefixed, path-specific advice `Ensure "PATH.pub" exists, or convert the private key "PATH" to a modern format with "ssh-keygen -p -m RFC4716"`. For `-i -`, the error is wrapped as `reading "-": failed to obtain public key for "-" SSH key`, followed after a blank line by the unprefixed advice `Use a file for which the corresponding ".pub" file exists, or convert the private key to a modern format with "ssh-keygen -p -m RFC4716"`. After decryption verify that private and public keys match. A matching malformed stanza with missing arguments reports `invalid ssh-ed25519 recipient block` or `invalid ssh-rsa recipient block` without prompting.

## Spec 15

Support hybrid native recipients produced by the harness: ML-KEM-768-X25519 (X-Wing) HPKE public/private keys encoded as in Spec 8. Its KEM identifier is `0x647a`. A serialized public key is the 1,184-byte ML-KEM-768 encapsulation key followed by the 32-byte X25519 public key; a serialized private key is a 32-byte master seed. Expand that seed with SHAKE256, reading the first 64 bytes as the ML-KEM-768 seed and the next 32 bytes as the X25519 scalar. Encapsulation concatenates the 1,088-byte ML-KEM ciphertext and 32-byte ephemeral X25519 public point. Its 32-byte KEM shared secret is SHA3-256 over `ssMLKEM || ssX25519 || ephemeralX25519 || recipientX25519 || domain`, where the six-byte ASCII `domain` is hexadecimal `5c 2e 2f 2f 5e 5c` (backslash, dot, slash, slash, caret, backslash). Decapsulation performs the same computation, with ML-KEM implicit rejection.

Use this KEM with HPKE Base mode, KDF identifier `0x0001` (HKDF-SHA-256), AEAD identifier `0x0003` (ChaCha20-Poly1305), and application info `age-encryption.org/mlkem768x25519`. Let `suiteID = "HPKE" || I2OSP(kemID,2) || I2OSP(0x0001,2) || I2OSP(0x0003,2)`, where `I2OSP` is unsigned big-endian. Define `LabeledExtract(salt,label,ikm) = HKDF-Extract(salt, "HPKE-v1" || suiteID || label || ikm)` and `LabeledExpand(prk,label,context,L) = HKDF-Expand(prk, I2OSP(L,2) || "HPKE-v1" || suiteID || label || context, L)`. Compute `pskIDHash=LabeledExtract(empty,"psk_id_hash",empty)`, `infoHash=LabeledExtract(empty,"info_hash",info)`, `context=0x00 || pskIDHash || infoHash`, `secret=LabeledExtract(sharedSecret,"secret",empty)`, `key=LabeledExpand(secret,"key",context,32)`, and `baseNonce=LabeledExpand(secret,"base_nonce",context,12)`. Seal the file key once with ChaCha20-Poly1305 nonce `baseNonce XOR I2OSP(0,12)` and empty associated data. HPKE sender setup yields encapsulation `enc`; emit type `mlkem768x25519`, one raw-Base64 `enc` argument, and the 32-byte sealed body. The matching identity opens it with the same computation; implicit-rejection/open failure is a nonmatch.

Hybrid recipients carry compatibility label `postquantum`. Every recipient in one operation must return the same sorted label set. Thus any mixture of hybrid/PQ recipients with classic X25519, SSH, or classic tag recipients fails exactly with `incompatible recipients: can't mix post-quantum and classic recipients, or the file would be vulnerable to quantum computers`. Multiple hybrid recipients and hybrid identities work, and files use the visible stanza type `mlkem768x25519`.

## Spec 16

Support public hardware-tag recipient encodings `age1tag1...` and `age1tagpq1...`. Decode them with the plugin-style Bech32 scheme: names are respectively `tag` and `tagpq`. A classic tag payload is exactly a compressed SEC1 P-256 public point (33 bytes), which must decode to a valid curve point. A hybrid tag payload is a valid ML-KEM-768-P256 HPKE public key. Malformed encodings, wrong sizes, invalid points, or invalid checksums report `malformed recipient "VALUE"`.

Classic tags use HPKE DHKEM(P-256) KEM identifier `0x0010`, HKDF-SHA-256, ChaCha20-Poly1305, Base mode, and info `age-encryption.org/p256tag`; the HPKE encapsulation is the 65-byte uncompressed SEC1 ephemeral point. For this DHKEM let `kemSuiteID="KEM" || I2OSP(0x0010,2)`, compute the P-256 ECDH value, set `kemContext=ephemeralPoint || recipientUncompressedPoint`, then apply the same labeled-extract/expand construction as Spec 15 but substituting `kemSuiteID`: `eaePRK=LabeledExtract(empty,"eae_prk",ECDH)` and `sharedSecret=LabeledExpand(eaePRK,"shared_secret",kemContext,32)`. Feed that result into the HPKE key schedule defined in Spec 15.

Hybrid tags use MLKEM768P256 KEM identifier `0x0050` with info `age-encryption.org/mlkem768p256tag`; its public key is the 1,184-byte ML-KEM key plus a 65-byte uncompressed P-256 point, its encapsulation is the 1,088-byte ML-KEM ciphertext plus a 65-byte ephemeral P-256 point, and its hybrid shared secret is `SHA3-256(ssMLKEM || ssP256 || ephemeralP256 || recipientP256 || "MLKEM768-P256")`. Feed that directly into the Spec 15 HPKE key schedule with KEM ID `0x0050`. Seal the file key with empty associated data. Compute a four-byte tag as follows: let `recipientPart` be the complete compressed 33-byte classic public key, or only the P-256 portion of the hybrid public key; let `rh4 = SHA256(recipientPart)[0:4]`; compute HKDF-Extract-SHA-256 with salt equal to UTF-8 info label and input key material `enc || rh4`, and take its first four bytes. Emit a stanza of type `p256tag` or `mlkem768p256tag`, arguments raw-Base64(tag) and raw-Base64(enc), and the sealed file-key body. Hybrid tag recipients carry `postquantum`; classic tags do not. Multiple same-class tag recipients are allowed. Decryption of tag recipients is expected through explicit harness-provided plugins, not a built-in private tag identity.

## Spec 17

All recipients specified across `-r`, `-R`, encryption-mode `-i`, and plugins wrap one common file key, yielding one or more independent stanzas; any corresponding identity can decrypt the entire file. Preserve supported mixed classic types (for example X25519 plus Ed25519 plus RSA, or classic tag plus classic types). Support at least 1,500 recipient stanzas, 1,000 direct/file recipients, dozens of identity files, and large data with many recipients within normal test time and memory limits.

Repeated identical CLI values remain functional but produce warnings. On the second and later occurrence write respectively `age: warning: duplicate recipient "VALUE"`, `age: warning: duplicate recipients file "PATH"`, or `age: warning: duplicate identity file "PATH"`. Detect duplicates even when separated by unrelated flags. Three occurrences may warn more than once, but at least one warning is required. Do not confuse different values or different recipient mechanisms as duplicates.

## Spec 18

ASCII armor (`-a`/`--armor`, encryption only) encodes the complete binary age file using standard padded Base64 in this exact envelope:

```text
-----BEGIN AGE ENCRYPTED FILE-----\n
BASE64 WRAPPED AT 64 CHARACTERS\n
-----END AGE ENCRYPTED FILE-----\n
```

There are no PEM headers or blank lines. Every nonfinal Base64 line is exactly 64 characters; the final line is at most 64 and uses canonical padding. If encoded data ends at a 64-character boundary, the footer begins on the next line without an extra blank line. Even encrypted empty plaintext has a nonempty age binary representation and a valid envelope. File and stdout destinations use identical structure.

Decryption auto-detects armor without `-a`, including up to 1,024 bytes of leading whitespace-only lines and up to 1,023 trailing whitespace bytes after the footer. LF and CRLF armor lines are accepted. More leading whitespace must not be accepted as armor (and will normally surface as an unexpected age intro); 1,024 or more trailing bytes reports `invalid armor: too much trailing whitespace`. Strictly reject a wrong/missing header, wrong/missing footer, EOF, an empty data line, a line over 64 characters, illegal or noncanonical Base64, or non-whitespace trailing bytes. Use diagnostics containing respectively `unexpected intro`/the observed first line, `invalid armor: invalid closing line`, `invalid armor: unexpected EOF`, `invalid armor: empty line in armored data`, `invalid armor: column limit exceeded`, `invalid armor: illegal base64 data`, and `invalid armor: trailing data after armored file`. An invalid closing line is quoted in the diagnostic: for observed line `-----END PEM FILE-----`, report `invalid armor: invalid closing line: "-----END PEM FILE-----"`, retaining the outer header-reading context. Binary age data must not be mistaken for armor.

## Spec 19

In decryption mode, parse the structural header before choosing a credential; this does not yet validate the semantic contents of a selected `scrypt` stanza. If no `-i` or `-j` was given, attempt automatic native passphrase decryption when the file has one `scrypt` stanza. A header containing two `scrypt` stanzas is rejected before prompting with `an scrypt recipient must be the only one`. A header without a sole usable `scrypt` stanza otherwise fails with `the file is not passphrase-encrypted, identities are required` and hint `specify identities with -i/--identity or -j to decrypt this file`.

When `-i` or `-j` supplies explicit identities, try those identities before applying the native-passphrase rejection, even when the header consists of a single `scrypt` stanza. This ordering is required because an explicitly selected plugin can intentionally implement that stanza type: in particular, `-d -j batchpass` must invoke batchpass and can successfully decrypt its `scrypt` output, or surface the plugin's `incorrect passphrase`, malformed-salt, malformed-work-factor, or maximum-work-factor error. If the supplied identities finish with nonmatches and no more specific error, a single-`scrypt` file then fails with `file is passphrase-encrypted but identities were specified with -i/--identity or -j` and the hint `remove all -i/--identity/-j flags to decrypt passphrase-encrypted files`. Thus an unrelated native identity still receives the passphrase-encrypted diagnostic, but the executable must not reject a `scrypt` file before giving a selected plugin the opportunity to handle it.

Try supplied identities until one unwraps the file key; native noninteractive identities may be prioritized ahead of interactive identities so an encrypted SSH key is not prompted for when another identity matches. A wrong identity must not abort attempts with later identities. If none match, fail with text containing `no identity matched any of the recipients`. Wrong keys produce no plaintext.

After a file key unwraps, verify the header MAC before reading plaintext, then authenticate every payload chunk. Header changes, including stanza corruption, therefore cannot be accepted even if a body happens to decrypt.

## Spec 20

Support the standard native `scrypt` stanza for `-p` encryption and automatic no-identity decryption. It is the only stanza in such a file and has `-> scrypt SALT LOGN`, where SALT is raw Base64 of a fresh 16-byte random salt and decimal `LOGN` is in 1..30 (normal interactive default 18). Derive a 32-byte key with scrypt using password bytes exactly as entered, salt `"age-encryption.org/v1/scrypt" || SALT`, parameters `N=2^LOGN, r=8, p=1`; wrap/open the 16-byte file key with ChaCha20-Poly1305, all-zero nonce, no associated data. Its recipient compatibility labels ensure it cannot be combined with any other recipient. Native automatic decryption obtains the passphrase before parsing or validating `SALT` and `LOGN`. Consequently, without a terminal, invalid salt `not_base64!`, nondecimal factor `nope`, and out-of-range factor `31` all exit 1 with `could not read passphrase: could not read passphrase: standard input is not a terminal, and /dev/tty is not available: open /dev/tty: no such device or address`, rather than a stanza-parameter error. Once a passphrase has been obtained, wrong password maps to `incorrect passphrase`, malformed salt to `failed to parse scrypt salt`, and nondecimal/out-of-range work factor to `scrypt work factor encoding invalid` or a clear bounds error.

`-p` obtains its passphrase from a controlling terminal, not from piped plaintext standard input. Decryption prompts once when appropriate. If no terminal is available, fail promptly rather than hang. Passphrase bytes are UTF-8-capable and are not arbitrarily truncated. Interactive terminal presentation is not otherwise fixed by this contract.

## Spec 21

Plugin recipient strings are Bech32 with HRP `age1NAME`; plugin identity strings use HRP `AGE-PLUGIN-NAME-` and uppercase encoding. A plugin name is nonempty and consists only of ASCII letters, digits, `+`, `-`, `.`, or `_`; parsed encodings normalize it to lowercase. In particular it must not contain `/`, `\\`, or any platform path separator. Reject malformed encodings and unsafe names rather than executing a path. `-j NAME` creates a valid data-less plugin identity and uses its corresponding identity-based recipient for encryption, or the identity for decryption.

For a plugin name `NAME`, locate and execute `age-plugin-NAME` from `PATH`. If absent, fail promptly and identify the attempted executable as `age-plugin-NAME`, include `plugin not found`, hint that the user might want to install the named plugin, and include `https://age-encryption.org/awesome#plugins`. Do not automatically execute a plugin merely because an input file contains an unknown stanza; loading requires an explicit recipient/identity/`-j` selection. Always wait for and reap plugin processes and close protocol pipes.

Once a string beginning with `age1` is structurally recognized as a plugin recipient, Bech32 failures use `invalid recipient encoding: REASON`, not the generic `malformed recipient` wrapper. This applies to plugin names containing allowed punctuation as well: `age1testplugin.foo-bar_baz1qdmzv9q` reports `invalid recipient encoding: invalid checksum`, and a mixed-case value such as `age1testplugin1INVALID!` reports `invalid recipient encoding: mixed case`.

## Spec 22

Implement the age plugin v1 client protocol used by harness-provided plugins. Invoke a wrapping plugin with exactly `--age-plugin=recipient-v1` and an unwrapping plugin with `--age-plugin=identity-v1`. Protocol messages use the same stanza serialization rules as the age header: `-> TYPE [ARG ...]\n`, a raw-Base64 body ending in a short line, and no enclosing file intro/footer.

For wrapping, send in order: `add-recipient ENCODING` (or `add-identity ENCODING` for an identity-based recipient), optionally one syntactically valid grease stanza whose type begins `grease-`, `wrap-file-key` with the 16-byte key in its body, bodyless `extension-labels`, and bodyless `done`. Then read responses until `done`. Each `recipient-stanza 0 TYPE [ARG ...]` becomes an age stanza with the returned body; require index zero and at least the index and type arguments, and acknowledge it with `ok`. Accept at most one bodyless `labels [LABEL ...]` response and acknowledge it with `ok`. A returned `error` body is acknowledged with `ok` and propagated as an error.

For unwrapping, send `add-identity ENCODING`, optionally grease as above, every candidate age stanza rewrapped as `recipient-stanza 0 TYPE [ARG ...]`, then `done`. Read until `done`; accept at most one `file-key 0` body, require index zero, and acknowledge it with `ok`. Absence of a file key is an identity nonmatch so later identities can be tried. A returned `error` is acknowledged and propagated. Unknown interactive extension requests must receive `unsupported`; `msg`, `request-secret`, `request-public`, and `confirm` receive `ok` on success or `fail` when unavailable/failed and are serviced through the terminal when available. Labels returned by plugins participate in the exact compatibility comparison of Spec 15.

This protocol must be sufficiently conformant for the harness `age-plugin-batchpass`: neither side may deadlock, protocol responses may not be dropped, multiple operations must not leak processes, and a normal plugin operation must produce a standard age header rather than a private file format.

## Spec 23

An external harness-provided `age-plugin-batchpass` is available on `PATH`; it is not part of `executable`. It is selected through `-e -j batchpass` and `-d -j batchpass`, and `executable` must discover it, inherit the caller's environment and open file descriptors, speak Spec 22, and surface its returned diagnostics. For clarity about the conditions the executable will encounter, this provided plugin reads either `AGE_PASSPHRASE` verbatim or the descriptor numbered by `AGE_PASSPHRASE_FD`; it strips trailing CR/LF bytes from descriptor input but preserves embedded newlines and other special/Unicode characters. Empty/unset values fail. Consequently, when both sources are set the executable's surfaced error contains `AGE_PASSPHRASE and AGE_PASSPHRASE_FD are mutually exclusive`, and when neither is set it contains `either AGE_PASSPHRASE or AGE_PASSPHRASE_FD must be set`.

The provided plugin returns a normal `scrypt` stanza as in Spec 20. In its environment, `AGE_PASSPHRASE_WORK_FACTOR` selects decimal `LOGN` (default 18), and values outside 1..30 return `AGE_PASSPHRASE_WORK_FACTOR must be between 1 and 30`; during opening, `AGE_PASSPHRASE_MAX_WORK_FACTOR` can reject a larger stanza with `scrypt work factor too large: N`. `executable` must preserve these errors rather than replacing them with an unrelated parse failure. A wrong password surfaces `batchpass plugin: incorrect passphrase` or at minimum `incorrect passphrase`. The labels returned by batchpass make it incompatible with any simultaneous native/SSH/PQ recipient. Empty, binary, armored, stdin/stdout, named-file, megabyte-scale, 500-character-password, and repeated round trips through the provided plugin must work.

## Spec 24

An identity file may itself be an age binary or armored file. Only a passphrase-encrypted (`scrypt`) age file is eligible for automatic interactive decryption as an identity file; decrypt it after obtaining a terminal passphrase, then parse its plaintext as the textual identity list from Spec 7. An age file encrypted to public-key recipients is not accepted merely because the caller has other identities; report that it is `encrypted with age but not with a passphrase`. If the passphrase is required but no terminal exists, both binary and armored encrypted identity files fail promptly with `failed to decrypt identity file: could not read passphrase: could not read passphrase: standard input is not a terminal, and /dev/tty is not available: open /dev/tty: no such device or address`. This diagnostic does not include the identity file path. Never treat arbitrary binary or a `-----BEGIN` malformed PEM as a valid identity list.

Encrypted SSH private-key prompting follows Spec 14. In particular, malformed/corrupt encrypted keys are errors, wrong-fingerprint keys do not prompt, and an unsupported encrypted DSA identity reports its unsupported type. A passphrase-protected RSA or Ed25519 identity can also be used with explicit `-e -i` to encrypt to its derived public key without decrypting the private material when its public portion is available.

## Spec 25

Input/output must be streaming in behavior and bounded independently of total plaintext size, aside from headers/recipient lists. It must successfully round-trip file and pipe inputs at sizes 0, 1, 65,535, 65,536, 65,537, exact multiple-chunk boundaries, 10 MiB, 50 MiB, and 100 MiB, including armor and large recipient sets. It must preserve byte-for-byte length and content and complete within the harness timeouts. Ciphertext overhead is exactly a 16-byte payload nonce plus 16 bytes per chunk plus the serialized header (armor adds only its envelope/newlines/Base64 expansion). Thus a 200 KiB plaintext has four chunk tags, and exact 64 KiB plaintext has one.

Failures must not leave newly requested output files behind when detected before the first write. A decryption error may leave only already-authenticated prior chunks if streaming to an output already opened, but must never release the failing or unauthenticated chunk. In the tested corruption cases, errors before payload authentication produce no expected complete plaintext.

## Spec 26

Ciphertext emitted by `executable` must be independently consumable by the harness-provided `age-inspect`, and ciphertext/key fixtures made by conforming age implementations must decrypt with `executable`. Observable stanza type names must be exactly `X25519`, `ssh-ed25519`, `ssh-rsa`, `scrypt`, `mlkem768x25519`, `p256tag`, and `mlkem768p256tag` as applicable. A one-X25519 header has the canonical structure and typically totals 168 bytes before its 16-byte payload nonce; adding another X25519 stanza grows it predictably. Inspectors must be able to find the closing line and compute payload size solely from the format.

Files generated for the same recipients need not be byte-identical and normally must differ, but the structure, algorithms, encodings, ordering, size accounting, and decryption result are deterministic given their random inputs. All fixed binary and armored age v1 fixtures, X25519/PQ/SSH identities, and mixed-recipient fixtures supplied to evaluation are within this contract and must be handled without relying on filenames or fixture-specific content.

## Spec 27

The following corruption classes must always fail rather than degrade to a wrong-key result or success: bad intro/magic; truncated header; missing or malformed stanza terminator; bad stanza Base64; wrong stanza argument counts; bad header MAC; missing 16-byte payload nonce; truncated, modified, reordered, or extended payload chunks; malformed armor; and trailing data after either armor or the final binary payload chunk. Expected distinguishing messages include `unexpected intro`, `failed to read header`, `invalid TYPE recipient block`, `bad header MAC`, `failed to decrypt and authenticate payload chunk`, `unexpected EOF`, `last chunk is empty, try age v1.0.0, and please consider reporting this`, and `trailing data after end of encrypted file`, according to the precise cases above.

Recipient/identity parse errors must occur before creating an output file. Wrong but well-formed identities instead reach identity selection and produce `no identity matched any of the recipients`. Unsupported or unknown header stanza types are safely ignored by identities that do not implement them; they never trigger arbitrary plugins. These rules, constant-time MAC/tag checks supplied by the cryptographic primitives, fresh randomness, strict canonical parsing, and the no-unauthenticated-output rule are required functional security behavior, not optional hardening.
